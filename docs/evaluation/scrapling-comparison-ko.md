# Scrapling vs 기존 스크래핑 도구 비교 (사내 도입 검토용)

> 기준: 이 문서는 **Scrapling 저장소의 공식 문서/코드 기준(버전 0.4.6)**으로 작성되었습니다.

## 1) 한눈에 보는 포지셔닝

- **Scrapling**: 파싱 + 정적/동적/스텔스 Fetcher + Spider(크롤러) + MCP를 하나로 통합한 “올인원” 성격.
- **BeautifulSoup/LXML 계열**: 파싱 특화(가볍고 단순), 수집/차단우회/크롤링 오케스트레이션은 별도 구성 필요.
- **Scrapy**: 대규모 크롤링/파이프라인 강점, 브라우저/스텔스는 추가 통합이 보통 필요.
- **Playwright/Selenium**: 동적 렌더링/자동화 강점, 크롤링 프레임워크/적응형 파싱은 별도 설계 필요.

## 2) 기능 비교표 (의사결정 핵심)

| 항목 | Scrapling | BeautifulSoup(+requests) | Scrapy | Playwright/Selenium 단독 |
|---|---|---|---|---|
| 파싱 성능/편의 | CSS/XPath + 확장 선택 API, 성능 벤치마크 제공 | 단순하고 익숙함, 대체로 느림(문서 기준) | 파서/셀렉터 성숙 | 렌더 후 파싱은 추가 코드 필요 |
| 사이트 변경 내성 | **Adaptive scraping**(요소 유사도 재탐색) | 기본 없음 | 기본 없음(커스텀 필요) | 기본 없음 |
| 동적 페이지 대응 | DynamicFetcher(Chromium/Chrome) | 없음 | 기본은 HTTP, 브라우저 연동 필요 | 강함 |
| 안티봇/스텔스 | StealthyFetcher, Turnstile/Interstitial 우회 지향 | 없음 | 기본 없음(커스텀) | 일부 가능(추가 stealth 튜닝 필요) |
| 프록시 로테이션 | 내장 ProxyRotator + 세션 단위 운영 | 직접 구현 | 가능(미들웨어) | 직접 구현/플러그인 |
| 크롤링 프레임워크 | Scrapy 유사 Spider + 체크포인트/스트리밍 | 없음 | 강함 | 없음 |
| Pause/Resume | `crawldir` 체크포인트 내장 | 없음 | `JOBDIR` | 없음 |
| 멀티세션 혼합 | HTTP/동적/스텔스 세션을 한 Spider에서 혼합 | 없음 | 확장은 가능하나 설계 부담 | 수동 설계 |
| AI/에이전트 연계 | MCP 서버 내장(선택자 기반 전달로 토큰 절감 지향) | 없음 | 기본 없음 | 도구화 필요 |
| 러닝커브 | 중간(기능 많음) | 낮음 | 중~높음 | 중간 |

## 3) Scrapling의 차별점 (기존 도구 대비)

### A. “적응형(Adaptive) 파싱”이 실무 유지보수 비용을 낮춤
- UI/DOM 개편 시 selector 깨짐을 **유사도 기반 재매칭**으로 완화.
- 장기 운영(가격/상품/채용/뉴스 수집 등)에서 **셀렉터 유지보수 빈도**를 줄일 잠재력이 큼.

### B. Fetching 레이어가 3단계로 나뉘어 운영전략 수립이 쉬움
- `Fetcher`(빠른 정적), `DynamicFetcher`(JS 렌더), `StealthyFetcher`(차단 회피 지향)를 동일 인터페이스로 제공.
- “실패 시 상위 난이도 fetcher로 승격” 같은 폴백 체인 설계가 단순.

### C. Spider 프레임워크가 실무 기능을 기본 제공
- 동시성/도메인별 지연/robots.txt/차단 감지 재시도/체크포인트 복구/스트리밍 출력 등 포함.
- Scrapy와 개념이 유사해 팀 온보딩이 상대적으로 수월.

### D. AI Agent 연동(MCP)이 실무 자동화에 유리
- 단순 본문 전체 전달이 아니라 CSS selector 기반으로 **필요 부분만 전달** 가능.
- 사내 LLM 파이프라인에서 토큰 비용/지연 최적화 여지가 큼.

## 4) 단점/리스크 (도입 전 반드시 확인)

1. **벤치마크는 프로젝트 자체 공개 수치**
   - 유리한 워크로드일 수 있으므로 사내 대상 사이트로 재현 벤치마크 필요.
2. **기능 통합의 반대급부: 운영 복잡도 증가 가능**
   - 브라우저 의존(fetchers extra, playwright/patchright), 프록시, 스텔스 설정까지 포함하면 DevOps 범위가 커짐.
3. **스텔스/우회는 대상 사이트 정책/법적 이슈 점검 필수**
   - 기술 가능 여부와 별개로 이용약관/법무 검토 필요.
4. **신규 프레임워크 락인 가능성**
   - 기존 Scrapy 파이프라인, 사내 공통 미들웨어와의 정합성 점검 필요.

## 7) 추천 도입 전략 (실행형)

### 권장: “전면 전환”보다 “2단계 병행 도입”

1. **Phase 1 (2~4주 POC)**
   - 대상 3개 사이트 선정: 정적 1, 동적 1, 차단강한 1.
   - 기존 스택 vs Scrapling 동시 측정:
     - 성공률(HTTP 200 + 필수 필드 추출률)
     - 평균 수집 시간
     - 차단률/재시도율
     - 유지보수 시간(selector 수정 횟수)
     - 인프라 비용(CPU/RAM/프록시)
2. **Phase 2 (점진 확장)**
   - Scrapling은 “변경 잦고 차단 강한 도메인”에 우선 적용.
   - 안정적인 정적 도메인은 기존 파이프라인 유지(혼합전략).

## 8) 결론 (의사결정 요약)

- **도입 적합한 경우**: 동적 페이지 비중 높고, 차단 대응 필요하며, DOM 변경이 잦아 유지보수 비용이 큰 조직.
- **보류/부분도입이 나은 경우**: 단순 정적 수집 위주 + 기존 Scrapy/BS4 파이프라인이 안정적으로 운영 중인 조직.
- 사내 상황이 “다양한 난이도의 사이트를 한 플랫폼에서 운영”이라면 Scrapling은 **강한 후보**.
